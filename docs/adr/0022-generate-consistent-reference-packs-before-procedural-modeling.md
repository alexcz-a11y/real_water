# Generate consistent Reference Packs before procedural modeling

Demonstration objects are generated as project-owned raster Reference Packs at an external image service driven through the agent browser, then reconstructed with img2threejs into independent code-only procedural Three.js models; generated pixels are evidence, not runtime meshes, and every pack is approved by a human before any reconstruction state opens. The Reference Bible in `docs/reference-bible.md` is the single specification for world, palette, materials, scale, neutral-reference lighting and framing, prompt invariants, and rejections; its prompt-invariant block is applied through the service's persistent per-conversation instructions rather than retyped, and this ADR records only the decision that the Bible governs. Each object begins with one canonical three-quarter identity anchor and, once that anchor is approved, derives every further view from it — accumulated into a saved service-side reference so identity tightens as views are approved — followed by front, side, back, and top elevations, material close-ups, and a wet look-dev view that is material evidence only. Independent angle prompts, silent identity drift, and claims about hidden geometry are rejected. The roughly 14 m twin-propulsion hero vessel is generated and approved first because it anchors the scale for the 2.4 m buoy, 1.2 m marine crate, 8 m underwater structure, and 250–300 m basalt sea stack; beyond that anchoring the remaining four assets carry no ordering constraint and their packs and reconstructions may proceed in parallel. Approved images are kept outside the repository at a stable local path so that every reconstruction worktree can read them, and the repository carries only their text evidence — final prompt, service identifiers, manual adjustments, date, approver, and per-file hashes — because a published MIT package must not carry hundreds of megabytes of raster evidence, and generated pixels were never runtime inputs.
